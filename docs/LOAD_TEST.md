# 1차 운영 조회 부하테스트

이 부하테스트는 Oracle Cloud 1GB Free Tier 운영 서버의 **공개 조회 API 처리 성능과 안정성**을 확인하기 위한 수동 테스트입니다. 운영 데이터를 변경하는 요청은 포함하지 않습니다.

## 테스트 범위

`SecurityConfig` 기준으로 인증 없이 허용된 다음 GET만 호출합니다.

- `GET /api/v1/notices?page={0..3}&size=20&sort=createdAt,desc` (약 65%)
- `GET /api/v1/notices?keyword={공지|장학|학사|행사}&page=0&size=20` (약 30%)
- `GET /api/v1/hello` (약 5%, 상태 확인용)

커뮤니티, 학사일정, 시간표 조회는 현재 `anyRequest().authenticated()`에 의해 인증이 필요하므로 제외했습니다. 공지 상세 조회는 조회수 변경 가능성이 있어 제외했습니다. 계정·JWT·임의 로그인은 사용하지 않습니다.

### 현재 비로그인 공개 범위

부하테스트 대상 선정 시 참고할 전체 공개 범위입니다. `SecurityConfig`의 `permitAll` 매처 기준입니다.

| 경로 | 비고 |
|---|---|
| `GET /api/v1/notices` | 목록·검색(`keyword` 파라미터), 페이징 |
| `GET /api/v1/notices/search` | 레거시 검색, 페이징 없음 |
| `GET /api/v1/notices/{id}` | 상세. 호출 시 조회수가 증가하므로 부하테스트에서 제외 |
| `GET /api/v1/hello` | 상태 확인 |
| `/uploads/**`, `/s3-uploads/**` | 첨부 파일 |
| `/api/v1/auth/**` | 인증 API (GET 외 포함) |

`GET /api/v1/notices/{id}/comments`는 2026-09-16부터 인증이 필요합니다. 댓글 응답에 작성자 실명과 회원 ID가 포함되기 때문입니다. 공개 범위를 넓히는 변경은 `NoticePublicAccessSecurityTest`가 막습니다.

## 부하 단계와 측정값

순차적으로 다음 단계가 실행됩니다.

`5 VU/1분 → 10 VU/2분 → 20 VU/2분 → 30 VU/2분 → 50 VU/2분`

50 VU 구간의 순간 지연을 재현할 때는 `soak` 프로필을 사용합니다.

`50 VU/10분 지속`

각 단계별로 한국어 로그와 Job Summary에 다음 값이 표시됩니다.

- RPS
- 평균 응답시간, p95, p99
- HTTP 실패율
- timeout/전송 오류 수
- 공지 목록·공지 검색·상태 확인별 RPS, 평균, p95, p99, 실패율, timeout 수

기본 threshold는 `HTTP 실패율 < 1%`, `p95 < 1000ms`입니다. threshold가 실패해도 k6 summary를 먼저 출력한 뒤 workflow를 실패 처리합니다.

## GitHub Actions에서 실행

실제 테스트는 자동 실행되지 않습니다. GitHub 저장소에서 다음 버튼을 사용합니다.

1. **Actions** 탭 → **k6 공개 조회 부하 테스트** 선택
2. **Run workflow** 클릭
3. `base_url`에 운영 API의 `https://` 주소 입력
4. `test_profile`에서 목적에 맞는 유형 선택
   - `staged`: 5→50 VU 단계별 기준 성능 확인
   - `soak`: 50 VU를 10분 유지하며 간헐적 병목 진단
5. **Run workflow** 재클릭
6. 실행된 Job의 로그 또는 **Summary**에서 단계별·요청 종류별 결과 확인

운영 URL은 workflow input으로만 주입되며 저장소 코드에 하드코딩하지 않습니다. 이번 1차 테스트가 안정적이어도 75/100 VU는 별도 실행에서 판단합니다.

### 실행 안전장치

- workflow는 `workflow_dispatch`로만 실행되며 push·PR 이벤트에는 연결되지 않습니다.
- 동일 workflow 실행은 `concurrency`로 직렬화되어 동시에 여러 부하를 만들지 않습니다.
- Job은 최대 18분 후 자동 중단됩니다.
- 실패율이 5% 이상이거나 전체 p95가 3초 이상인 상태가 1분 뒤에도 이어지면 조기 중단됩니다.
- `base_url`이 비어 있거나 HTTPS가 아니면 실행 전에 실패합니다.
- `localhost`, `127.0.0.0/8`, `0.0.0.0`, `::1` 대상은 실행 전에 차단합니다.
- GitHub Actions 권한은 `contents: read`만 사용합니다.

## 운영 서버 리소스 확인

추가 인프라(Prometheus/Grafana)는 설치하지 않습니다. GitHub Actions가 부하테스트 실행 중 30초마다 운영 서버에 읽기 전용 SSH 명령을 실행하고, 다음 정보를 Job Summary에 기록합니다.

```bash
# 전체 CPU/RAM 및 컨테이너별 메모리/CPU
docker stats --no-stream

# 메모리(MB), swap 포함
free -m

# 컨테이너 재시작 여부를 포함한 상태
docker ps --format "table {{.Names}}\t{{.Status}}"
```

기록할 항목은 전체 메모리 사용량·swap, 백엔드/DB 컨테이너 CPU·메모리와 컨테이너 상태입니다. 이 명령들은 읽기 전용이며 서버 설정을 변경하지 않습니다. 접속에는 배포 workflow에서 이미 사용하는 `SERVER_IP`, `SERVER_USER`, `SSH_PRIVATE_KEY` GitHub Actions Secret을 재사용합니다.

테스트 종료 시 다음 진단도 함께 기록합니다.

- 백엔드·MySQL·Nginx 컨테이너의 재시작 횟수, OOM 종료 여부, 최종 상태
- 테스트 시작 이후 백엔드 로그 중 `warn`, `error`, `exception`, `timeout`, `hikari`, `connection`이 포함된 최근 200줄

서버 자원은 백엔드 CPU 최대 128.75%·메모리 최대 210.5MiB/450MiB, MySQL CPU 최대 50.47%·메모리 최대 25.5MiB/350MiB였습니다. 호스트 메모리는 최대 645MiB/954MiB가 사용됐고 available 메모리는 최소 308MiB였습니다. 백엔드·MySQL·Nginx 모두 `RestartCount=0`, `OOMKilled=false`, `Status=running`이었으며 테스트 구간 백엔드 경고·오류 로그는 없었습니다.

목록·검색·DB를 사용하지 않는 상태 확인에서 p99와 실패율이 비슷하게 나타났습니다. 따라서 이번 timeout을 검색 쿼리나 HikariCP 연결 풀 고갈로 판단할 근거는 없습니다. 공통 경로인 호스트 CPU 스케줄링, Nginx, TLS·네트워크 구간의 간헐적 지연이 더 우선적인 후보입니다.

운영 대책은 다음과 같습니다.

1. 현재 HikariCP 최대 5개와 MySQL 메모리 설정을 유지합니다. DB 병목 증거 없이 연결 풀을 늘리면 1GB 서버의 메모리 여유만 줄어듭니다.
2. 일반 운영 권장 범위는 40 VU 이하로 두고, 50 VU는 통과 가능한 상한 검증 구간으로 관리합니다. 50 VU에서도 기준은 통과하지만 timeout이 0은 아닙니다.
3. 다음 지속 테스트에서는 k6의 연결 대기·TCP 연결·TLS 협상·서버 대기 시간을 분리하여 공통 경로 중 지연 위치를 확인합니다.
4. 같은 현상이 실제 사용자 트래픽에서도 확인될 때만 Nginx upstream keepalive와 호스트 CPU 사용률을 전후 비교합니다. 설정은 한 항목씩 변경하고 동일한 `soak` 테스트로 회귀 검증합니다.
5. 실패율 1% 또는 p95 1초를 넘으면 신규 부하 확대를 중단합니다. 실패율 5% 또는 p95 3초가 지속되면 자동 조기 중단 안전장치를 유지합니다.

## 50 VU 간헐적 지연 진단과 대응 기준

현재 증거로는 CPU·메모리 포화가 확인되지 않았습니다. 운영 HikariCP 연결 풀은 최대 5개이므로 연결 대기, 검색 쿼리 지연, 외부 네트워크 지연을 후보로 두되 원인을 확정하지 않습니다. `soak` 결과의 요청 종류별 지표와 종료 진단을 다음 기준으로 해석합니다.

| 관찰 결과 | 판단 | 우선 대응 |
|---|---|---|
| 검색만 p95/p99 또는 실패율 상승 | `%keyword%` 검색 쿼리 병목 가능성 | 실행 계획과 데이터 건수를 확인하고 전문검색 또는 검색 전용 인덱스를 검토 |
| 목록·검색이 함께 느리고 Hikari timeout/connection 경고 발생 | DB 연결 풀 대기 가능성 | DB 연결 수와 메모리를 확인한 후 풀을 5→8로 한 단계만 조정하고 동일 테스트 재실행 |
| 상태 확인까지 동시에 느리고 애플리케이션 경고가 없음 | Nginx·호스트·네트워크 병목 가능성 | Nginx 오류 로그, 호스트 load average, 패킷 손실을 별도 확인 |
| OOM 또는 컨테이너 재시작 발생 | 메모리 한계 초과 | 즉시 부하를 중단하고 JVM/컨테이너 메모리 배분을 먼저 조정 |
| 10분 동안 기준 통과, 오류 로그 없음 | 50 VU 지속 처리 가능 | 현재 설정을 유지하고 정기 배포 후 회귀 테스트로 사용 |

연결 풀이나 컨테이너 제한은 측정 결과 없이 변경하지 않습니다. 변경할 때는 한 항목만 조정하고 같은 `soak` 프로필을 다시 실행하여 전후 수치를 이 문서에 추가합니다.
